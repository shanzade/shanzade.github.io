qt5 信号槽与 moc 机制的正向和逆向学习

2026-11-10

什么是信号槽

信号槽是 Qt 暴露给开发者的通信范式，而标准 C++ 语法本身并不支持 signals、slots 这类关键字，也没有内建的反射机制。
虽然说，c++ 可以通过回调函数等机制实现类似的功能，但是很明显，这些做法都会产生较大的耦合。
MOC（Meta-Object Compiler，元对象编译器）正是 Qt 引入的代码生成预编译器，它会在 C++ 编译器介入之前扫描带有 Q_OBJECT 宏的头文件，自动生成一个 moc_*.cpp 文件，在其中实现信号函数的具体逻辑与元对象反射表。

信号槽机制的使用

Q_OBJECT 宏是使用 Qt 信号槽机制的”入场券”。
任何想要发出信号 / 拥有槽函数的类，都必须同时满足三个条件：

  1. 直接或间接继承自 QObject
  2. 在类声明里写上 Q_OBJECT 宏
  3. 让构建系统对这个头文件跑一次 moc（Meta-Object Compiler），生成一份额外的 C++ 源文件（本项目里是 moc_counter.cpp）

emit 并不是 C++ 的原生关键字，它在 Qt 源码里其实是一个空宏，也就是 #define emit。你在代码里写 emit valueChanged(10);，对于 C++ 编译器来说等同于直接调用成员函数 valueChanged(10)。那么这个函数的实现写在哪里？这就是 MOC 做的事情：在头文件里你只需要声明 signals: void valueChanged(int);，而函数体由 MOC 自动生成在 moc_counter.cpp 中。MOC 生成的实现会去查找所有连接到这个信号的槽函数并依次调用。所以，emit 只是一个视觉标记，用来提醒阅读代码的人“这里正在触发一个信号”，核心的调度逻辑全在 MOC 生成的代码与 QObject 内部的连接列表里。

如果在槽函数中继续编写 emit xxsignal(yy); 的话，就表明信号层层传递。比如一个网络管理类收到低层 Socket 的“原始字节到达”槽函数通知，在槽里把字节解析成了业务数据包，接着在同一个槽里 emit packetReady(packet)，把更高层级的信号抛给 UI 或业务模块。

大致情况如下：

[ 普通成员函数 / lambda 函数 ] -- 其他的一些逻辑
    ↑
    |
    |  （通过 `QObject::connect()` 绑定）
    |
[ 信号 signal ] -- 只写声明，不写实现 -- MOC -- 自动生成 moc_*.cpp，会自动给信号生成真正的函数体
    |
    |  （通过 `QObject::connect()` 绑定）
    |
    ↓
[ 槽 slot ] -- 自定义逻辑；Qt 自动在信号发出时调用槽函数
class Counter : public QObject
public slots:
    // 槽（slot）：本质上就是一个普通的成员函数，只是额外"挂了号"，
    // 使得它可以被 QObject::connect() 绑定到某个信号上——
    // 信号发出时，Qt 会自动帮你调用这个函数，不需要手写回调分发代码。
    void increment();
    void reset();
    void setValue(int newValue);
signals:
    // 信号（signal）：只写声明，不写实现。
    // moc 会在 moc_counter.cpp 里把它"实现"为一段真正的函数体，
    // 作用就是：遍历所有连接到它的槽，依次调用。
    // 你自己永远不需要、也不能去实现 signals 下面的函数。
    void valueChanged(int newValue);
    void reachedLimit(const QString &message);
void Counter::setValue(int newValue)
{
    if (newValue == m_value)
        return; // 值没变就不发信号，避免无意义的通知（Qt 自己的很多 setter 也是这个套路）

    m_value = newValue;

    // emit 只是一个空宏（#define emit），真正"通知所有槽"的分发代码
    // 是 moc 在 moc_counter.cpp 里帮你生成、实现出来的。
    emit valueChanged(m_value);

    if (m_value >= kLimit) {
        emit reachedLimit(QString("Counter reached limit: %1").arg(m_value));
    }
}

connect 语法如下：

QObject::connect(sender, &SenderClass::signalName, receiver, &ReceiverClass::slotName);

其中前两个参数指明由哪个对象的哪个信号触发，后两个参数指明通知哪个对象的哪个槽函数。
如果是连接到 Lambda 表达式或者普通独立函数，就可以省略 receiver，直接写成：

QObject::connect(sender, &SenderClass::signalName, functor);

例子：

// 写法一：信号连接到 lambda —— 最常见、最直观的用法。
QObject::connect(&counter, &Counter::valueChanged, [](int v) {
    qDebug() << "[lambda slot] counter value changed to" << v;
});
// 写法二：信号连接到另一个 QObject 的槽函数。
// 效果：counter 每次 setValue，mirror 都会被同步设置成一样的值。
QObject::connect(&counter, &Counter::valueChanged, &mirror, &Counter::setValue);

void Counter::qt_static_metacall(QObject *_o, QMetaObject::Call _c, int _id, void **_a)
{
    auto *_t = static_cast<Counter *>(_o);
    if (_c == QMetaObject::InvokeMetaMethod) {
        switch (_id) {
        case 0: _t->valueChanged((*reinterpret_cast<std::add_pointer_t<int>>(_a[1]))); break;
        case 1: _t->reachedLimit((*reinterpret_cast<std::add_pointer_t<QString>>(_a[1]))); break;
        case 2: _t->increment(); break;
        case 3: _t->reset(); break;
        case 4: _t->setValue((*reinterpret_cast<std::add_pointer_t<int>>(_a[1]))); break;
        default: ;
        }
    }
    if (_c == QMetaObject::IndexOfMethod) {
        if (QtMocHelpers::indexOfMethod<void (Counter::*)(int )>(_a, &Counter::valueChanged, 0))
            return;
        if (QtMocHelpers::indexOfMethod<void (Counter::*)(const QString & )>(_a, &Counter::reachedLimit, 1))
            return;
    }
}

const QMetaObject *Counter::metaObject() const
{
    return QObject::d_ptr->metaObject ? QObject::d_ptr->dynamicMetaObject() : &staticMetaObject;
}

void *Counter::qt_metacast(const char *_clname)
{
    if (!_clname) return nullptr;
    if (!strcmp(_clname, qt_staticMetaObjectStaticContent<qt_meta_tag_ZN7CounterE_t>.strings))
        return static_cast<void*>(this);
    return QObject::qt_metacast(_clname);
}

int Counter::qt_metacall(QMetaObject::Call _c, int _id, void **_a)
{
    _id = QObject::qt_metacall(_c, _id, _a);
    if (_id < 0)
        return _id;
    if (_c == QMetaObject::InvokeMetaMethod) {
        if (_id < 5)
            qt_static_metacall(this, _c, _id, _a);
        _id -= 5;
    }
    if (_c == QMetaObject::RegisterMethodArgumentMetaType) {
        if (_id < 5)
            *reinterpret_cast<QMetaType *>(_a[0]) = QMetaType();
        _id -= 5;
    }
    return _id;
}

qt_static_metacall 核心分发函数，每一个信号和槽都有一个整数编号。当 qt 运行时决定调用某个方法时，就会把这个编号传进来。
例如，通过 case 4: _t->setValue(...) 把传入的通配参数指针 _a[1] 强转回 int，从而调用到成员函数。

// SIGNAL 0
void Counter::valueChanged(int _t1)
{
    QMetaObject::activate<void>(this, &staticMetaObject, 0, nullptr, _t1);
}

// SIGNAL 1
void Counter::reachedLimit(const QString & _t1)
{
    QMetaObject::activate<void>(this, &staticMetaObject, 1, nullptr, _t1);
}

信号函数实现，也就是 Counter::valueChanged 和 Counter::reachedLimit。
均只有一行调用；例如，在代码里执行 emit valueChanged(val) 时，实际执行的就是这里的函数，把信号编号（这里是 0）和参数 _t1 打包交给 Qt 底层的事件激活分发器。

activate(QObject 信号对象, QMetaObject 元数据对象, index 信号索引, ???)

继续深入理解。

valueChanged 和 reachedLimit 这两个信号实现，在业务代码中主动触发时（例如 emit valueChanged(10); 或者直接 counter.valueChanged(10);），编译器会直接跳进这两个函数，调用 QMetaObject::activate，某种程度上充当了事件分发的发起者。

Counter::qt_static_metacall 则是在事件分发的末端由 Qt 运行时底层调用的。当 QMetaObject::activate 接收到信号触发请求后，它会去查找内部维护的连接列表。如果发现目标接收者是一个 QObject 槽函数，激活引擎就会把信号附带的参数打包成一个通配指针数组 void **_a，然后回调接收者对象的 qt_static_metacall，并传入对应的槽函数编号 _id。进入这个函数后，通过内部的 switch-case 匹配，将参数指针强转并真正执行你的槽函数代码，比如 _t->setValue(...)。

此外，qt_static_metacall 在编译期和连接建立阶段（比如调用 QObject::connect 时）也会被内部调用，主要用于通过 IndexOfMethod 分支来反查某个信号或槽函数指针在元对象表中的具体索引编号。

编译

编译期主要产生四块内容：字符串池、元数据表、信号函数体、metacall 分发表。

字符串池

类名、信号名、槽名、参数类型名拼接为以 \0 分隔的连续字符数组。

static const qt_meta_stringdata_MyObject_t qt_meta_stringdata_MyObject = {
    {
        QT_MOC_LITERAL(0, 0, 8),   // "MyObject"
        QT_MOC_LITERAL(1, 9, 8),   // "mySignal"
        QT_MOC_LITERAL(2, 18, 13), // "anotherSignal"
        QT_MOC_LITERAL(3, 32, 6),  // "mySlot"
        QT_MOC_LITERAL(4, 39, 5),  // "reset"
        QT_MOC_LITERAL(5, 45, 3),  // "int"
        QT_MOC_LITERAL(6, 49, 4)   // "void"
    },
    "MyObject\0mySignal\0anotherSignal\0mySlot\0reset\0int\0void\0"
};

QT_MOC_LITERAL(idx, ofs, len) 存储相对偏移量而非指针，字符串池和索引数组均为只读，无需加载时地址重定位，可放入共享段。

qt_static_metacall 分发表

_id 是方法相对索引，_a[0] 是返回值，_a[1] 起是参数。IndexOfMethod 用于新式 connect，把函数指针映射为整数索引。

void MyObject::qt_static_metacall(QObject *_o,
                                  QMetaObject::Call _c,
                                  int _id,
                                  void **_a)
{
    if (_c == QMetaObject::InvokeMetaMethod) {
        auto _t = static_cast<MyObject *>(_o);

        switch (_id) {
        case 0:
            _t->mySignal(*reinterpret_cast<int *>(_a[1]));
            break;
        case 1:
            _t->anotherSignal();
            break;
        case 2:
            _t->mySlot(*reinterpret_cast<int *>(_a[1]));
            break;
        case 3:
            _t->reset();
            break;
        }
    } else if (_c == QMetaObject::IndexOfMethod) {
        int *result = reinterpret_cast<int *>(_a[0]);

        {
            using _t = void (MyObject::*)(int);

            if (reinterpret_cast<_t *>(_a[1]) ==
                static_cast<_t>(&MyObject::mySignal)) {
                *result = 0;
                return;
            }
        }
        // ... 其他 IndexOfMethod 分支
    }
}

运行时

连接链表

connect() 最终调用 QObjectPrivate::addConnection，把连接插入发送者的 connectionLists。它以 signalIndex 为下标，每个元素是 ConnectionList。

struct QObjectPrivate::ConnectionList {
    QAtomicPointer<Connection> first; // 链表头
    QAtomicPointer<Connection> last;  // 链表尾，使 append 为 O(1)
};

last 同时充当发射期间遍历的哨兵，避免遍历到发射过程中新加入的连接。

Connection 的双重链表

struct Connection {
    QObject *sender;
    QObject *receiver;
    int signal_index;
    int method_index;      // 槽在接收者元对象中的索引
    int connectionType;    // Auto/Direct/Queued/BlockingQueued

    Connection *nextConnectionList; // ① 同一信号下的接收者链表
    Connection *next;               // ② 发送者的 senders 链表
    Connection **prev;              // ② 的二级指针
};
  • nextConnectionList：同一信号下所有接收者链表，activate 时遍历。
  • next / prev：发送者的 senders 链表，用于销毁时 O(1) 断开所有连接。

prev 指向本对象 senders 表头的地址，删除节点可直接 *c->prev = c->next，无需查找前驱。
双重链表体现空间换时间：正向链表 nextConnectionList 用于高效发射，反向链表 senders 用于高效断开，prev 二级指针实现 O(1) 删除。

新式 connect 的索引转换

connect(sender, &MyObject::mySignal,
        receiver, &MyObject::mySlot);

编译期得到成员函数指针，连接存储需要整数索引，由 IndexOfMethod 完成转换；connect 函数模板在编译期验证信号与槽的参数兼容性，不兼容签名无法通过编译。

函数指针 &MyObject::mySignal
→ static_metacall(IndexOfMethod, 0, args)
→ qt_static_metacall 进入 IndexOfMethod 分支
→ 比较函数指针，*result = 0
→ signalOffset() 转为 signalIndex
→ connectionLists[signalIndex] 创建 Connection

activate 分发

基本入口

void QMetaObject::activate(QObject *sender,
                           const QMetaObject *m,
                           int local_signal_index,
                           void **argv)
{
    int signal_index = m->methodOffset() + local_signal_index;

    QObjectPrivate *sp = QObjectPrivate::get(sender);

    if (!sp->connections)
        return;

    if (sp->threadData->thread != QThread::currentThread()) {
        queued_activate(sender, signal_index, argv);// 不是当前线程（跨线程）QueuedConnection
        return;
    }

    activate_sender(sender, signal_index, argv, sp->connections);// 同线程 DirectConnection
}

其中 signal_index = methodOffset() + local_signal_index 是绝对信号索引。

activate_sender 最终是一个循环，见下面的“同线程 DirectConnection”。

同线程 DirectConnection

以下 while 循环即 activate_sender 的简化主体，遍历 connectionLists[signal_index]，对每个 Connection 按连接类型分流。

while (c) {
    QObject *receiver = c->receiver;

    if (c->isSlotObject) {
        c->slotObj->call(receiver, argv); // 新式语法：直接调用
    } else {
        QMetaObject::metacall(receiver,
                              QMetaObject::InvokeMetaMethod,
                              c->method_index,
                              argv);      // 旧式语法：索引分发
    }

    c = c->nextConnectionList;
}

旧式语法经 qt_metacall 的 switch 跳转；新式语法 slotObj->call() 直接执行函数指针或仿函数，绕过元对象索引，性能更好。

以 emit obj->mySignal(42) 为例，完整路径为：

① moc 生成的 mySignal 被调用
   void *_a[] = { nullptr, &_t1 };

   ↓
② activate 计算绝对索引

   ↓

解析字符串数据

此处的字符串是一个 qt_meta_stringdata_xx 结构体，不同于普通的 char* 或者 std::string。

struct qt_meta_stringdata_Example_t {
    QByteArrayData data[N];
    char stringdata0[K];
};

data[i] 是字符串描述记录，字符串正文集中存储在后面的字符区。

Qt 5 的 QByteArrayData 基于 QArrayData。常见 x64 记录大小为 0x18：

偏移 大小 含义
+0x00 4 引用计数；静态记录通常是 -1，即 0xFFFFFFFF
+0x04 4 字符串字节长度，不含终止 NUL
+0x08 4 分配容量及标志位
+0x0C 4 常见 x64 对齐填充
+0x10 8 有符号 qptrdiff offset

注意引用计数 0xFFFFFFFF 不是分隔符，不能通过搜索它来判断每条记录的边界。

设字符串描述表基址为 S，第 i 条记录地址为 H_i：

H_i = S + i * 0x18
length_i = read_int32(H_i + 0x04)
offset_i = read_int64(H_i + 0x10)
字符串地址 = H_i + offset_i

注意，offset 相对各自的 QByteArrayData 记录起始地址（H_i），不是统一相对 S。length 也是同理。

源码的 QArrayData::data() 明确是 this + offset。

常见 x86 布局记录大小为 0x10，offset 在 +0x0C，宽度为 4 字节；不能沿用 x64 的 0x18 步长。
空字符串也是合法记录，常用于空 tag 或未命名参数。

  • 各个 ...Data 是以 uint 为单位的表内索引；

方法表地址计算：

methodCount = U32(D + 0x10)
methodData  = U32(D + 0x14)
methodTable = D + 4 * methodData

接下来解析函数数组 / 方法表。

struct MethodEntry5 {
    uint32_t name;
    uint32_t argc;
    uint32_t parameters;
    uint32_t tag;
    uint32_t flags;
};
字段 解释
name 方法名的字符串索引，用于前面解析字符串数组（注意是从 0 开始）
argc 参数数量
parameters 参数描述块相对 D 的 uint 索引，即 元数据起始地址+ i_parameters * 4
tag 方法标签的字符串索引，通常指向空字符串
flags 访问级别、方法种类和附加标志

其中，参数 parameters 的第一个成员为返回值，中间部分由 argc 决定数量，每个参数以 4字节参数类型 + 4字节参数名称 组成。

至于为什么是 i * 4，是因为元数据表是 uint 数组，每个元素占 4 字节。0x30 表示从表头开始偏移多少个数组元素，不是字节数，所以换算为字节偏移要乘 4。

另外解释一下似乎不太常用的 tag 和 flags。
tag 是 moc 保存的额外方法标签，可以通过 QMetaMethod::tag() 取得。它通常不参与普通信号槽分发。
如：

#ifndef Q_MOC_RUN
#define MY_TAG
#endif

class Example : public QObject {
    Q_OBJECT
private slots:
    MY_TAG void inspect();
};

编译器看到的是合法函数声明；moc 可以保存 MY_TAG。表中的 tag 字段保存其字符串索引。空 tag 的索引不一定是 0，0 往往是类名。

flags 在 qt5 下常见定义：

掩码/位 值 含义
AccessMask 0x03 低两位为访问级别
AccessPrivate 0x00 private
AccessProtected 0x01 protected
AccessPublic 0x02 public
MethodTypeMask 0x0C 方法种类掩码
MethodMethod 0x00 普通元方法
MethodSignal 0x04 信号

MethodConstructor 0x0C 构造记录

例如 0x06 是 public signal，0x08 是 private slot，0x0A 是 public slot。不要只判断 flags & 0x04 是否非零，因为构造记录的类型位 0x0C 也含有这一位。

moc 通常按“信号 → 槽 → 普通元方法”生成主方法表，因此前 signalCount 项是信号；剩余项不能一概叫槽，应继续解析 flags。

默认参数可能使一个源函数对应多条元方法记录。例如槽 void save(int mode = 0) 可能出现 save(int) 和克隆的 save()，所以表项数量不必等于源代码中的独立函数数量。

其他细节

怎样确认信号实际连接了哪个函数

（部分内容来自 ai，可能有误）

旧式字符串连接
connect(sender, SIGNAL(changed(int,int)),
        receiver, SLOT(handlePair(int,int)));

常见二进制字符串含有类别前缀：

2changed(int,int)
1handlePair(int,int)

2 表示 SIGNAL，1 表示 SLOT。部分构建还可能附带源码位置信息。搜索这些字符串并查看 connect 调用，可恢复发送对象、接收对象、签名和连接类型。

新式函数指针连接
connect(sender, &Sender::changed,
        receiver, &Receiver::handlePair);

这种形式不一定保留可直接搜索的连接签名字符串。可从构造函数、初始化代码中的 connect 模板实例、connectImpl 及槽对象包装代码继续分析。

新式连接允许普通成员函数、lambda 或其他可调用对象作为接收目标：

connect(sender, &Sender::changed, context,
        [](int x, int y) { /* 业务逻辑 */ });

该 lambda 不会仅因被连接就自动出现在类的槽方法表中。某些新式连接会通过槽对象包装器直接调用目标，因此一次信号不保证经过接收类的 qt_static_metacall。

自动连接

形如：

QMetaObject::connectSlotsByName(this);

需检查对象树中的 objectName 和以下命名模式：

void on_<objectName>_<signalName>(...);

例如按钮对象名为 button1，对应处理函数可能叫 on_button1_clicked()。所以找不到显式的 connect 调用，也不意味着没有连接。

运行时验证
  1. 在信号发射函数下断点，记录发送对象和参数。
  2. 确认具体的 activate 重载及其信号编号含义。
  3. 沿信号投递代码观察目标接收对象或槽包装器。
  4. 在候选业务函数入口下断点，验证实际命中和参数值。
队列连接改变调用栈
连接方式 执行方式 调试表现
DirectConnection 在发射线程同步调用 通常可沿发射调用栈跟入目标
QueuedConnection 投递事件，在接收对象所属线程稍后调用 发射栈和接收栈通常分开
AutoConnection 发射时按当前线程与接收对象线程的关系选择 可能同步，也可能排队
BlockingQueuedConnection 排队调用，发射线程等待完成 跨线程等待；同线程使用可能死锁

其中 AutoConnection 的判断涉及发射时当前执行线程，不能只比较发送对象与接收对象的线程归属。接收线程还需要有可处理事件的事件循环。对于排队调用，可以继续观察元调用事件的创建与处理，而不能只用“单步没有立即进入槽”判断连接失效。

对于采用 offsetsAndSizes 的 qt 6 字符串布局，设字符串结构基址为 S6：

offset_i = U32(S6 + 8*i)
length_i = U32(S6 + 8*i + 4)
正文地址 = S6 + offset_i

这与 qt 5 的“当前记录地址 + offset”不同。

较新的 Qt 6 moc 还使用辅助模板生成数据，实际逆向分析应同时核对目标版本的 generator.cpp、qmetaobject_p.h、QMetaMethod::Data 定义和格式 revision。

一套可以执行的逆向顺序

  1. 确认环境。 记录 Qt 版本、编译器、位数及是否静态链接。
  2. 取得元对象。 从对象虚表识别 metaObject()，或从类名字符串反查。
  3. 验证布局。 检查父类、字符串、整数表和分发函数指针是否合理。
  4. 恢复字符串。 Qt 5 按各记录自身的相对 offset 计算，不把它当成指针数组。
  5. 读取表头。 获取 methodCount、methodData、signalCount。
  6. 解析方法记录。 恢复名称、参数、返回类型、tag、访问级别及方法种类。
  7. 标明编号空间。 区分本类局部编号、公开方法索引和信号专用编号。
  8. 定位代码。 到静态分发函数的 InvokeMetaMethod 分支追踪对应编号。
  9. 确认业务路径。 信号向上查发射位置、向下查连接目标；槽继续分析实际逻辑。
  10. 动态验证。 记录真实对象、参数和线程，确认命中的目标。

如果字符串正常而方法表从第二项开始全错，优先排查步长和 Qt 版本；如果方法名正确但找不到对应 case，优先排查 _c 分支和编号空间；如果信号断点命中但槽不命中，继续排查连接方式、lambda 包装器、事件循环及断点是否下在实际实现上。
