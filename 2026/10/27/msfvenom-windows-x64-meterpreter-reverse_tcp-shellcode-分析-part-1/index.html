初始化

shellcode 前三行：

为什么说 call notepad.FFD03646 是将接下来的 shellcode 地址放到栈上呢？
双击过去看看：

是一个 pop rbp。也就是说，call 的过程中会自动将 call 之后的下一条指令的地址，放到栈上，而 pop rbp 则会将 rsp 指向的内容给到 rbp，即 rbp 将会存放call 之后的下一条指令的地址，通过这种方式完成了地址的记录。

那，为什么正好就跳到了这个位置？
其实这里的 call notepad.FFD03646 是调试器解析有误，此处的 call ?? ?? ?? ?? 后面四个字节是偏移，小端序，即 0xCC。
加上跳转规则：目标地址 = 当前指令地址 + 指令本身长度 + 偏移量
最终总共是 0xD1 个字节距离，575h + 0d1h = 646h。
对于 jcc 指令来说，这条规则同样适用。

接下来是两块内容的初始化，一是 dll 字符串，二是一个 sockaddr_in 结构体。

字符串显而易见。

sockaddr_in 结构体定义如下。
其中要注意的是，sin_port 和 sin_addr 都是大端序，使用 htons 和 htonl 进行转换。

struct sockaddr_in {
     short            sin_family;    // 2 字节 ，地址族，e.g. AF_INET, AF_INET6
     unsigned short   sin_port;      // 2 字节 ，16位TCP/UDP 端口号 e.g. htons(3490)，
     struct in_addr   sin_addr;      // 4 字节 ，32位IP地址
     char             sin_zero[8];   // 8 字节 ，不使用

字段 内容 解释
sin_family 0002 地址族
sin_port 115ch（大端） 端口号
sin_addr C0 A8 EE 82（大端） ip 地址

最终，r14 存放 ws2_32 dll 字符串指针，r12 存放 sockaddr_in 的结构体指针。

查找与调用函数

通过简单地计算哈希来查找函数。


先将 rcx 设置为字符串地址，然后将 r10d 设置为一个完全看不懂的数值，call rbp 回到刚才设下的 shellcode 位置。
好像啥也看不懂。双击 call 看看做了什么。


先是 push 了一堆寄存器，可以猜测后面的操作会影响到这些寄存器的原有值。
中间还夹了一个非常经典的操作：mov rdx, qword ptr gs:[rdx+60]。这个指令正是从 teb 中获取 peb。

teb：thread environment block，线程环境块（TEB 结构）可保存线程的上下文信息。详情见 msdn。在 windbg 中输入 dt _TEB 可以查看。
peb：process environment block，Contains process information.详情见 msdn，在 windbg 中输入 dt_PEB 可以查看。
简单来说，通过这两个块可以获取到很多信息，最主要的就是，通过 PEB 可以获取到该进程中加载了的 dll 模块及其相关信息。

这一部分主要就是将 rdx 设置为 peb 的地址。

ldr。

如果去查找 _LIST_ENTRY 这个结构体的话，会发现这个结构体完全和 rdx+4ah 搭不上边，因为这个结构体里面只有两个成员。

//0x10 bytes (sizeof)
struct _LIST_ENTRY
{

其实，InLoadOrderModuleList、InMemoryOrderModuleList、InInitializationOrderModuleList 这三个成员，本质上都是 _LDR_DATA_TABLE_ENTRY 结构体类型。（使用 _LIST_ENTRY 应该只是为了方便遍历？）
https://www.vergiliusproject.com/kernels/x64/windows-7/sp1/_LDR_DATA_TABLE_ENTRY

//0xe0 bytes (sizeof)
struct _LDR_DATA_TABLE_ENTRY
{
    struct _LIST_ENTRY InLoadOrderLinks;                                    //0x0
    struct _LIST_ENTRY InMemoryOrderLinks;                                  //0x10
    struct _LIST_ENTRY InInitializationOrderLinks;                          //0x20
    VOID* DllBase;                                                          //0x30
    VOID* EntryPoint;                                                       //0x38
    ULONG SizeOfImage;                                                      //0x40
    struct _UNICODE_STRING FullDllName;                                     //0x48
    struct _UNICODE_STRING BaseDllName;                                     //0x58
    ULONG Flags;                                                            //0x68
    USHORT LoadCount;                                                       //0x6c

接下来我们就可以解析 rdx+4ah 是什么了？还不行。
这里有一个非常大的前提条件，就是前面提到的 InLoadOrderModuleList、InMemoryOrderModuleList、InInitializationOrderModuleList 这三个成员，它们分别对应到 _LDR_DATA_TABLE_ENTRY 结构体对应成员的位置，即

  • InLoadOrderModuleList 会指向 InLoadOrderLinks（距 _LDR_DATA_TABLE_ENTRY 0 偏移）的位置，而
  • InMemoryOrderModuleList 会指向 InMemoryOrderLinks（距 _LDR_DATA_TABLE_ENTRY 0x10 偏移）的位置
  • InInitializationOrderModuleList 会指向 InInitializationOrderLinks（距 _LDR_DATA_TABLE_ENTRY 0x20 偏移）的位置

也就是说，rdx+4ah，通过前面的 InMemoryOrderModuleList 0x10 偏移之后，对应的应该是结构体 0x5a 的位置，在 BaseDllName 里面，而不是 FullDllName（前者 Base 是只记录 dll 文件名称，而后者 Full 除了记录 dll 名称之外还会记录其所在路径）。
https://www.vergiliusproject.com/kernels/x64/windows-7/sp1/_UNICODE_STRING

//0x10 bytes (sizeof)
struct _UNICODE_STRING
{
    USHORT Length;                                                          //0x0
    USHORT MaximumLength;                                                   //0x2
    USHORT* Buffer;                                                         //0x8
};

最终，rcx 存放被遍历的 dll 的 BaseDllName 中 MaximumLength 的值，rsi 存放 BaseDllName 中的 Buffer，即 dll 名称字符串。

计算 dll 文件名的哈希。

xor rax, rax 清空不多说。
lodsb 是一个指令，会从 ds:si（ds:rsi） 中加载一个字节到 al，与其对应的还有 lodsw，加载一个字（2 个字节）到 ax。并且还会判断 df 标志位，如果 df=0 那么每加载一个字节就令 si +1，这也就是为什么最开始需要 cld 令 df=0。

cmp al, 61、jl 0x2、sub al, 20 这三者构成了最简单的小写转大写功能。首先判断字符是否是大写，0x61 对应的是小写的 a。
jl 0x2 小于跳转，根据上面的跳转规则来看此处偏移总共是 4，即跳到 35a7 的位置。
sub al, 20 将小写转大写，例如 61h - 20h = 41h 对应大写的 A。
其实说“小写转大写”也不太恰当，因为 ascii 表里面小写字母后面还有其他可见字符。此处估计没有考虑这么多。

ror r9d, D 将 r9d 循环右移 13 位。然后 add r9d, eax 将刚才加载的字符（经过变换后）存到 r9d 寄存器。
最后 loop 0xed，是什么意思呢？

E2 cb LOOP rel8   Decrement count; jump short if count != 0。

即，一个循环。使用的寄存器是 ecx，正好对应前面提取 MaximumLength 即 dll 文件名字符串的长度。
这里的 rel8 是有符号数，0xed 即十进制下的 -19。
回顾前面提到的跳转偏移计算规则，计算地址的距离 35ae + 指令长度 2 - 359d = 0x13 = 19，二者正好对应，于是跳回到 xor rax, rax 准备清空字符，并令 ecx 计数器 -1。非常巧妙。

最终 r9d 存放了 BaseDllName 的一串小哈希。

检查导出表。

将当前 dll / _LDR_DATA_TABLE_ENTRY 指针压到栈上存下来，以及对应的 dll hash 也留到栈上。

回顾先前的内容，rdx+20 在这里应该是 rdx+30，对应了 _LDR_DATA_TABLE_ENTRY 的 DllBase 成员，这个指针指向了一块区域，这块区域存放着对应 pe 文件在硬盘上原有的样子（即，pe 结构以文件形式存放在硬盘上，与被加载到内存中，是两种不同的情况，这里 DllBase 指的是前者）。
随后 rdx+3c，熟悉 pe 结构的话就能知道，这里是 pe 结构里面的 e_lfanew，对应文件中 _IMAGE_NT_HEADERS 的偏移。
通过 rax + rdx 就可以得到 _IMAGE_NT_HEADERS。
接下来 rax+18h 读取 pe 位数，如果不是 64 位的话就跳出去了。

typedef struct _IMAGE_NT_HEADERS {
 DWORD Signature; // PE标识  0
 IMAGE_FILE_HEADER FileHeader; // 标准PE头  4
 IMAGE_OPTIONAL_HEADER32 OptionalHeader; // 扩展PE头  18h
} IMAGE_NT_HEADERS32, *PIMAGE_NT_HEADERS32;

typedef struct _IMAGE_FILE_HEADER {

最后 rax+88 获取导出表 rva，如果导出表是空的话也是直接跳出去了。

两个 jcc 计算规则和上面一样，这里就不多说了。
跳转的位置如下。

把刚才 push 进来的两项内容 pop 回去，然后通过解析 [rdx] 继续转到下一个 _LDR_DATA_TABLE_ENTRY / dll / pe，并回到一开始获取 BaseDllName 的位置（movzx rcx,word ptr ds:[rdx+4A]）。

总的来说，就是检查了 pe / dll 的位数以及导出表情况，通过这两种方式提前排除掉不匹配的 dll。

解析导出表，找到指定的函数。

在检查完导出表 rva 不为 0 之后，就跳转到导出表的对应位置。
其中 rax+20、rax+18 均与下面这个结构体有关，这两者解析了导出表中的 AddressOfNames 和 NumberOfNames 这两个字段，用于查找导出表中的函数名称。

typedef struct _IMAGE_EXPORT_DIRECTORY {
    DWORD   Characteristics; 0
    DWORD   TimeDateStamp; +4
    WORD    MajorVersion; +8
    WORD    MinorVersion; +0Ah
    DWORD   Name;　+0Ch
    DWORD   Base; +10h
    DWORD   NumberOfFunctions;  +14h
    DWORD   NumberOfNames; +18h
    DWORD   AddressOfFunctions; +1ch
    DWORD   AddressOfNames; +20h
    DWORD   AddressOfNameOrdinals; +24h
} IMAGE_EXPORT_DIRECTORY, *PIMAGE_EXPORT_DIRECTORY;

最终 r8d 存放 AddressOfNames 指针，ecx 存放函数名个数。

清空 r9 寄存器用于存放哈希结果。rcx -1 用于计数（NumberOfNames 记录了有多少个函数名称，该值 -1 正好是指向最后一个函数名）。
[r8+rcx*4] 解析每一个函数名 rva，与存放 DllBase 的 rdx 进行相加，就可以跳转到对应函数名的位置。

清空 rax 用于给 lodsb 加载字符。ror r9d, D 和之前一样计算哈希。

cmp al, ah 是什么意思呢？lodsb 会从 ds:si 加载一个字节到 al，而 xor rax, rax 会清空整个 ax，所以说 ah 寄存器在这一块永远都是 0，即，用一种巧妙的方式判断 al 是否为空字符。
最后 jne 回到 xor rax, rax，继续下一个字符的计算。


[rsp+8] 对应了先前的 push r9 dll hash，即，将本次计算函数的 hash 和 dll hash 相加，然后比较 r10d，这也就解释了为什么之前 call rbp 的时候需要先令 r10d 为一个看不懂的值。
jne 跳回到 jrcxz 的位置，比较是否已经遍历完该 dll 下所有带名字的导出函数。
如果 jrcxz 判断到 rcx=0 的话，就表明没有在该 dll 中找到对应的函数，继续下一个 dll 的查找。


如果上面 jne 没有跳出来，即 r9d 计算得到的哈希与 r10d 目标一致，表示已经找到了所需要的函数，这时候就会进行 AddressOfNameOrdinals 和 AddressOfFunctions 的查找，通过索引反推函数 rva 索引，最后将 rva 同 dll 地址相加，得到最终的函数地址。（回顾上面的 _IMAGE_EXPORT_DIRECTORY 结构体）

总结

  • 学习到了 call/jmp 的配合，即利用库函数的 ret 实现地址的返回，减少开销。
  • 学习到了有关 stager shellcode 的基本内容，即通过 ws2_32 建立通信。
  • 加深了对通过 LDR 链表进行函数查找的理解。
